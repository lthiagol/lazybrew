## Findings
- **F-01 | major |** G-3: the install / uninstall / task-completion emitters are unprotected. Mutating `gui.go:302` (`TaskCompletedMsg`, brew-update), `:345` (`TaskCompletedMsg`), `:385` (`MutationResultMsg`) to `RefreshMsg{LoadOutdated: true}` leaves `go test ./internal/gui/... -count=1` fully green — only the tick has a structural test. **Proof:** apply the mutation, run that command → all `ok`. **Fix:** a test that sends `TaskCompletedMsg` and `MutationResultMsg` and asserts the emitted `RefreshMsg` has `LoadOutdated == false` (mirroring `TestAutoRefreshTickStaysCacheOnly`). The code is correct today, but the exact M9 regression this slice forbids would ship unnoticed.
- **F-02 | major |** G-4 / AC-04: the cache-survival behaviour has no test. Nothing asserts that a status refresh keeps `KeyOutdatedFormulae`/`KeyOutdatedCasks`, or that the dashboard still shows the count after a plain refresh. Under N5 the only failure is a call-count side effect in the load test (fixable by bumping the expected count to 2 — after which nothing notices). A throwaway probe written during this review (prime both outdated keys, send `RefreshMsg{}`, assert the cache still holds the key and the dashboard renders `Outdated:  1 packages`) **passes** on current code and **fails** under N5 → the missing test is viable and biting; it was deleted before reporting. **Fix:** add that test to AC-05.
- **F-03 | minor |** G-3 "R from any panel loads the count": with `brew.update_on_start: true` (non-default; default `false`, `internal/config/config.go:70`) the first `R` takes `gui.go:569-586`, which enqueues `brew update` and returns **no** `RefreshMsg`; the follow-up refresh comes from the task-completion path (plain `RefreshMsg{}`) and the `update` invalidation drops the outdated keys, so the count stays "not loaded" until `R` is pressed again. **Proof:** `sed -n '569,596p' internal/gui/gui.go`. **Fix:** emit `RefreshMsg{LoadOutdated: true}` alongside the update task, or set the flag on the follow-up refresh.
